Why the single-stream gain is so large

GB10 has roughly 273 GB/s of memory bandwidth. Decoding one token means streaming all 22 GB of NVFP4 weights through it once, which puts a hard ceiling near 12 tok/s. The baseline measures 11.55 — about 94% of roofline. Decoding here is almost purely bandwidth-bound, and the GPU's math units sit idle.

That is the ideal case for speculation. DFlash2 drafts 7 tokens and the target verifies them in a single weight-streaming pass, committing 6.38 of them on average. The idle FLOPs become tokens. The 4.70× here beats the 3.43× the z-lab card reports on an H200 precisely because this box is more bandwidth-starved than an H200 — there is simply more headroom to reclaim.

Acceptance length also beats the card's reported 4.4–5.5, for a duller reason: those numbers are at temperature 1.0, and this run is greedy, which is much easier to draft for.

And why it narrows under load

The gain falls from 4.70× to 2.94× to 2.61× as concurrency rises, which is expected: batching already amortizes weight streaming across requests, so the spare bandwidth speculation was exploiting is progressively consumed. Two things are worth noting anyway — system-wide throughput still climbs (49 → 108 tok/s), and TTFT degrades slightly under speculation (0.131 → 0.275 s). Drafting cannot help prefill and adds a little per-step overhead, so if your workload is dominated by short completions, measure before adopting.

Is the output actually unchanged?

DFlash2 is advertised as lossless, so greedy output should match the baseline exactly. It almost does — and the gap is not a verifier bug.

Diffing the generations shows a divergence at character 110 of 389, inside the model's thinking block: "Need concise but show reasoning." versus "Provide reasoning." Everything after </think> — the entire user-visible answer — is character-for-character identical.

The cause is reproducible with no drafter involved anywhere. Against the plain baseline server, the same prompt at temperature 0 run alone twice is identical; run inside a batch of 8 it diverges — at the same character 110. The engine is not bitwise-reproducible across batch shapes, because a different batch shape selects different GEMM tilings and reduction orders, and NVFP4's coarse quantization makes near-ties common. Speculative decoding necessarily changes batch shape — it verifies N positions per forward pass instead of 1 — so it inherits exactly that sensitivity.

The guarantee, stated precisely DFlash2's losslessness is distributional and assumes exact arithmetic. It does not promise bitwise-identical output under a quantized target with shape-dependent kernels. The correct check is that the final answer is unchanged — and it is. determinism_test.py in the repo demonstrates the effect without any drafter.

Two things that cost real time

1. A host-RAM OOM that looks like a GPU-memory bug

On first startup FlashInfer JIT-builds its NVFP4 CUTLASS GEMM (fp4_gemm_cutlass_sm120) during profile_run. Left unbounded, ninja fans out to nproc (20 here) parallel jobs, each nvcc cicc peaking near 7 GB RSS. On unified memory that races the 22 GB of resident weights, the OOM killer takes ninja, and the engine dies with a bare CalledProcessError … returned non-zero exit status 137.

The traceback lies It points at determine_available_memory, which reads like a GPU-memory problem. It is not — it is host RAM, during kernel compilation. Capping MAX_JOBS (serve.sh sets 4) fixes it.

2. The "unquantized LM head" requirement is gone

The DFlash2 model card and the dfischermittwald/Qwen3.8-27B-NVFP4-DFlash2 repo both warn that DFlash2 rejects a quantized target LM head: 

ValueError: DFlash2 requires an unquantized target LM head for candidate TopK

That guard lived in the unmerged PR (vllm-project/vllm#52816). In released 0.28.0 it is gone — LogitsProcessor._apply_head dispatches through lm_head.quant_method.apply(…), which handles a quantized head fine. So the mainstream unsloth NVFP4 checkpoint works and the specially-requantized fork is not needed. If a future version reinstates the guard, that repo is a drop-in replacement for TARGET in serve.sh.

The stack

GPUNVIDIA GB10 (Grace-Blackwell), compute capability 12.1 (sm_121), 121 GB unified memory, aarch64
vLLM0.28.0 (PyPI manylinux_2_28_aarch64 wheel)
PyTorch2.13.0+cu130
Target modelunsloth/Qwen3.8-27B-NVFP4 — ~22 GB, NVFP4 weights, FP8 lm_head
Draft modelz-lab/Qwen3.8-27B-DFlash2 — 3.85 GB, bf16

Two hardware notes. vLLM's bundled cubins target sm_120; CUDA guarantees binary compatibility across minor revisions within a major architecture, so they run on sm_121. And because memory is unified, --gpu-memory-utilization is a fraction of the whole 121 GB the desktop session also lives in — it is set conservatively to 0.60. NVFP4 was not optional here: bf16 weights (56 GB) do not fit the budget.

Reproducing this

git clone https://github.com/madeye/qwen3.8-dflash2-gb10
cd qwen3.8-dflash2-gb10
./fetch_weights.sh            # ~26 GB of checkpoints

./run_all.sh                  # base vs dflash at concurrency 1 / 4 / 8
MODES="base mtp dflash" ./run_all.sh   # add Qwen3.8's built-in MTP head

run_all.sh writes per-mode JSON plus the generated text into results/ and prints the comparison table. check_lossless.py diffs baseline against speculative output, and determinism_test.py reproduces the batch-shape sensitivity described above with no drafter in the loop.
